# Кейс 2: реальный баг на железе — камера «молчит», а не ошибается

## Контекст

CV-пайплайн контроля качества, реальная камера на Jetson Orin Nano,
журнал дрейфа модели и буфер неуверенных кадров для последующей приёмки.
Демо-режим (`--demo`) на подставной камере проходил чисто. Реальный
режим (`02-run-hardware.sh`) заваливал **каждый** кадр одной и той же
ошибкой:

```
Камера не отдала кадр: Камера не открыта — вызовите open()
```

## Диагноз

Первое впечатление — проблема с OpenCV или с самим железом камеры. Это
оказалось не так: причина — в порядке вызовов, а не в драйвере.

`run_hardware.py` строил конвейер (`build_pipeline`) и сразу запускал
цикл чтения кадров, ни разу не вызвав `pipeline.open()`:

```python
pipeline = build_pipeline(
    config=config, db_logger=db_logger, metrics=metrics, run_id=args.run_id, **parts
)
pipeline.open()   # ← этого вызова не было в исходной версии
```

Баг маскировался в демо-режиме, потому что подставная камера (`StubCamera`)
считается открытой уже в конструкторе. У настоящей камеры объект
`_capture` остаётся `None`, пока `open()` не вызван явно — симулятор и
реальность здесь молчаливо разошлись в предположении о жизненном цикле
объекта, и ни один тест на подставной камере этого не поймал бы в
принципе: сама природа расхождения — в реальном железе, а не в логике.

## Исправление — не только код, но и сообщение об ошибке

```python
def open(self) -> None:
    """
    Открыть камеру перед первым кадром.

    Без этого вызова `JetsonCamera.read()` недели 7 падает на каждом
    кадре с «Камера не открыта — вызовите open()», маскируя настоящую
    причину (нет шлейфа/устройства, OpenCV без GStreamer и т.д.) —
    `open()` отдаёт её один раз при старте, а не 300 раз в журнале.
    `StubCamera` демо-режима уже открыта в конструкторе, вызов — no-op.
    """
    opener = getattr(self._camera, "open", None)
    if callable(opener):
        opener()
```

После фикса реальный прогон либо заработает, либо упадёт **один раз** на
старте с содержательной причиной — не 300 одинаковых строк, которые
нужно было бы прокручивать, чтобы понять, что все они об одном и том же.
Это разница между «починили баг» и «починили то, что инженер увидит в
2 часа ночи при реальном инциденте на линии».

## Почему это сильнее «чистого кода»

Любой код может скрывать ошибку в предположении о жизненном цикле
объекта — проверка типов и юнит-тесты на подставных объектах этого не
ловят, потому что подставной объект как раз и воплощает упрощённое
предположение. Находит это только прогон на реальном железе и разбор
причины вместо патча симптома (например, «просто обернуть в try/except»
скрыл бы баг, не исправив его).
