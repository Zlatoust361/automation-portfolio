# Кейсы: промышленная автоматизация + edge AI на реальном железе

[![tests](https://github.com/Zlatoust361/automation-portfolio/actions/workflows/ci.yml/badge.svg)](https://github.com/Zlatoust361/automation-portfolio/actions/workflows/ci.yml)
[![license: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

Три самостоятельных технических кейса из более крупного проекта
(24-недельный курс промышленной автоматизации с реальным Jetson Orin
Nano, ПЛК, камерой и манипулятором). Здесь — не весь проект, а три
точки, которые можно разобрать в деталях на любом уровне глубины:
реальный найденный баг, архитектурное решение с ценой ошибки, защита
линии от зависания на реальном железе.

## Как это делалось — честно

Реализация написана с помощью Claude Code под моей архитектурой,
критериями приёмки и ревью. Я не скрываю инструмент — в 2026 это норма
для сильных инженерных команд, а не повод для подозрений. Что
действительно моё в каждом кейсе — архитектурное решение, критерий
приёмки и разбор причины конкретного бага; в README каждого кейса это
явно отделено от кода, который реализация сгенерировала по этим
требованиям.

Я готов разобрать любой из трёх кейсов на любом уровне глубины вживую —
это и есть настоящая проверка, не текст в README.

## Кейсы

| Кейс | О чём | Что показывает |
|---|---|---|
| [`case-1-jetson-plc-watchdog/`](case-1-jetson-plc-watchdog/) | Watchdog вокруг CV-инференса на реальном Jetson, с измеренным запасом по времени | Инженерная дисциплина: что происходит, когда реальное железо не отвечает вовремя, а не просто «код работает» |
| [`case-2-drift-detection-bug/`](case-2-drift-detection-bug/) | Реальный баг на железе: камера молча не открыта, 300 одинаковых ошибок вместо одной содержательной | Умение найти причину, а не симптом — и почему сообщение об ошибке само по себе часть инженерной работы |
| [`case-3-pid-antiwindup/`](case-3-pid-antiwindup/) | PID-регулятор с антивиндапом и контринтуитивным фактом про D-составляющую | Доменное суждение, которое невозможно сгенерировать не понимая теорию управления |

## Проверить самому

```bash
pip install pytest
python -m pytest case-1-jetson-plc-watchdog   # возврат управления через timeout_s, защёлка, зависшие потоки
python -m pytest case-3-pid-antiwindup        # антивиндап (1000 тактов в насыщении), производная по измерению, факт про D
```

Тесты закрепляют числами то, что в README каждого кейса заявлено
словами: интеграл без антивиндапа уходит за 50000, с ним остаётся <100;
при зависшем инференсе `run()` возвращается через таймаут, а не через
длительность инференса; на объекте первого порядка D увеличивает
перерегулирование. Кейс 2 — разбор бага, кода для тестирования в нём
нет намеренно. CI гоняет это на Python 3.10 (JetPack 6) и 3.12.

## Источник

Выдержки из более крупного учебного репозитория (24 недели + два
опциональных трека, Jetson Orin Nano, реальный ПЛК, камера, манипулятор).
Полный репозиторий — отдельный продукт, не публикуется здесь целиком.

## Как это обновляется

Источник истины — закрытая монорепа курса; сюда попадает не новый код, а новая находка. Процедура, шаблон кейса и очередь кандидатов — в [`UPDATING.md`](UPDATING.md); зеркало с источником держит [`.portfolio/sync.py`](.portfolio/sync.py).
